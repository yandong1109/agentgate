# 需求评审议程

> **定位**：与需求基线（`requirements-baseline-zh.md`）配套的评审议程；基线是"要什么"的唯一权威，本文件是"还有哪些待评审假设、待澄清问题、关键裁定、待补充项"，随评审推进持续更新。
> **用法**：评审时逐项关闭 §1 待评审假设；§2 待澄清问题、§3 关键裁定、§4 补充项作为推进依据。

---

## 1. 待评审的设计假设

本节不是需求，是设计现状的评审输入。既有实现与架构中出现的对象模型与模块划分，"如何满足上述需求"取决于这些设计是否成立。以下初判供设计评审使用，不代表需求立场：

**判据**：内聚性（一个东西只做一件事）、依赖方向（不来回指向）、自然缝隙（是否领域固有）、变则同变（改一处是否牵连多处）。

| 设计项 | 初判 | 依据 |
| --- | --- | --- |
| 用例 / 评测集 / 评估器 / 评测 / 门禁 / 调用链 这些概念 | 成立 | 领域固有词汇，对应真实工作 |
| "评测集目录 + 版本载体"拆成两个对象 | 可疑 | 用户只需"评测集有版本"，是否要两个对象待审 |
| 评测时把整份评测集复制进配置 | 可疑 | "可复现"是需求，整份复制是代价，是否过度待审 |
| 调用链按五种类别（路由/对象/工具/状态/事件）切分 | 可疑 | 从可观测领域借来，评测只需能提取路由/工具/状态/输出 |
| 指标按"指标 → 维度 → 类别 → 总分"四层聚合 | 可疑 | 属"如何算分"，层次是否过度待审 |
| 评估器也要草稿/发布流程 | 可疑 | 从"A/B 用同一评估器"推不出"要有发布流" |
| 静态检查作为独立顶级能力域 | 可疑 | 概念承袭自外部平台，自身价值存疑 |

这份清单应在设计评审中逐项关闭，而不应在需求里默认坐实。

## 3. 关键裁定

以下为本基线对几处临界取舍的裁定结论（详细理由见基线 §7 关键决策）：

| 议题 | 本基线裁定 |
| --- | --- |
| 静态检查优先级 | 后置 P2（D2） |
| 门禁归属 | 补录为 P0（REQ-022） |
| 采样 | 定为 P3 待定（REQ-009） |
| 调度（预约 / 通知 / 智能建议） | 拆分：异步执行 P0，预约 P2（D3） |
| 结果对比 | 定为 P1 通用能力，A/B 为其子集 |
| 优先级批量调整 | 报告下钻（023）、单用例重跑（027）升 P0；语义评测（014）升 P1；自动生成用例（010）、断点恢复（036）降 P2；采样（009）降 P3；用例回写（011）定为 P1（简版列于第一阶段但未实现，后置实现） |
| 脱敏优先级 | 降为 P2，脱敏机制保留、暂按「采集侧已脱敏」对待，字段范围与强度后置（待确认外部数据是否已脱敏后详细设计） |
| 旧文档第二阶段四项处置 | 完整版本血缘图、文件与多模态产物评估、CI/CD 上线门禁、调优建议采纳闭环：有意暂缓，待有明确需求再增补，已入基线 §2.4 |
| 需求文档关系 | 不取代简版需求（`product-requirements-zh.md`）：简版为入口概览，基线为其详细展开与需求细目权威，不一致处以基线为准 |
| 结果指标口径 | REQ-021 吸纳简版明确列出的统计维度：按用例类别/难度通过率、分项准确率（路由/触发/工具调用）、Badcase 分布、失败率 |

## 4. 需求补充项清单

> **目的**：让需求基线不仅能陈述"要什么"，还能直接支撑 AI 助手完成设计分析、代码实现与测试验收。编号 G（gap）；"必须补"=不补则验收不可执行，"建议补"=提升切片后多人/AI 协作质量。

### 4.1 必须补

| 编号 | 补充项 | 现状问题 | 改进动作 | 关联需求 |
| --- | --- | --- | --- | --- |
| G1 | 验收标准可执行化 | 不少验收是"一句话结论"，或兜底标注"待澄清" | 每条 REQ 补「正常路径 + 异常路径」两个可判定条件，尽量写成 Given-When-Then 或"输入 → 预期输出/状态" | 全量；重点 REQ-009/015/020/021/025/031/032/033 |
| G2 | 跨能力异常/容错矩阵 | 中断、超时、外部对象不可用、评审输出异常等散落在各 REQ，易漏 | 汇总一张表：异常场景 → 期望行为 → 是否计入失败（区别于"对象失败"） | REQ-014/017/018/019/036/035 |
| G3 | NFR 可量化验收 | "可复现=结果相同"中"相同"未定义；性能指标依赖部署规模而缺判定点 | 明确"复跑后指标/结论逐字段一致"；性能留占位判定口径 | §6 可复现 / 安全 |

**验收写法约定（执行 G1 时的统一口径）**：每条验收至少覆盖 ① 正常路径（应满足）② 异常/边界路径（出错了怎么办）。示例——REQ-016「结果五态」可写成："给定一个评审返回格式异常的语义标准，当执行评测时，则该用例判为『评测出错』，且不导致整次评测失败、不计数进通过率"。

### 4.2 建议补

| 编号 | 补充项 | 现状问题 | 改进动作 | 关联需求 |
| --- | --- | --- | --- | --- |
| G4 | 需求依赖/前置显式化 | 依赖方向只在 `capability-domains-zh.md`，切片后单看某条 REQ 不知道先后 | 每条 REQ 加"依赖/前置"字段 | 全量 |
| G5 | 领域概念关系 + 关键属性表 | 用例/评测集/版本/评估器等关键字段散在 REQ-004/006/007 | 集中一节列关键属性与关系（仍属领域层，非设计） | REQ-004/005/006/007/012 |
| G6 | 端到端验收场景 walk-through | 缺"接入对象 → 产出报告"的完整叙述，AI 易只见树木 | 补 1-2 条端到端场景 | §1 / §5 主线 |
| G7 | 需求意图/背景补充 | 需求只有"做什么"，缺"为什么这么定"的意图 | 为每类需求补一句领域动机/背景，帮助评审与 AI 助手理解 | 全量 |
| G8 | 用例健康度 + flaky 检测隔离（后置能力） | 缺"跨多次运行"的用例稳定/失败统计视角，无法识别"总是失败"与"忽好忽坏"的用例 | 后置新增能力：① 用例结果历史与失败频率统计；② flaky 自动识别并隔离（可选不计入门禁） | 关联 REQ-023/026/028/029 |
