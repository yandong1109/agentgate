# AgentGate 聚焦交付计划 V4.1（目标优先阅读版）

> 状态：Ready for kickoff，可直接用于任务沟通、认领和验收  
> 代码基线：当前集成分支 `integration/p1-new`；启动时再次确认分支与提交  
> 团队：共 5 人，均使用 AI 助手，其中 2 人对 AI 使用和业务尚不熟悉；A～E 只表示职责  
> 推进口径：按依赖、完成证据和验收门禁推进，不预设工作日窗口  
> 版本范围：内部 Alpha；未完成认证、完整脱敏和生产恢复前，不宣称可处理未脱敏生产数据或支持正式多用户环境

---

## 1. 这份计划怎么读

这份计划同时提供两个视角，使用同一套 R 编号：

- **先按能力看**：第 3、4 章。先了解第一波和第二波每个 R 解决什么问题、谁参与、做到什么样。
- **再按人看**：第 5 章。理解共同目标后，每个人再看自己的第一步、为了哪些 R 工作、要交付什么。

`R` 表示一个可独立验收的能力包，不表示所有 R 必须按编号串行开发：

- 第一波中，R1 异步、R2 真实 Agent、R4 LLM 评估器可以并行；R3 真实 Skill 在 R2 的共用 Target 协议稳定后加入。
- 第二波中，R5 用例生成、R6 结果对比、R7 根因分析可以并行；R8 A/B Test 依赖 R6 的完整 Run 对比。
- `G1/G2` 是联合验收门禁，不是新的功能模块。

每个 R 统一使用四种状态：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 进入条件尚未满足，或者尚未认领 |
| 进行中 | 已有负责人和可运行分支，但完成标准尚未全部通过 |
| 可验收 | 主责人认为完成，等待独立验收人执行验收脚本 |
| 完成 | 真实主路径、关键异常、自动化测试和演示证据全部通过 |
| 阻塞 | 外部条件或上游契约缺失；需写明解除条件和推动人 |

## 2. 目标、现状与交付地图

### 2.1 本轮只解决八项能力

第一波：先让系统真正能评测。

1. R1：任务异步管理与可靠执行。
2. R2：接入真实 HTTP Agent 并形成真实报告。
3. R3：用同一套评测链路评测真实 Skill。
4. R4：接入真实 LLM 评估器，完成主观评测。

第二波：让真实结果能辅助决策。

1. R5：自动生成候选用例并人工审核入库。
2. R6：比较两个完整 Run。
3. R7：对 Badcase 给出有证据的根因假设。
4. R8：对两个对象版本进行受控 A/B Test。

不影响八项能力的其他事项全部暂缓，见第 6 章。

### 2.2 当前代码起点

| 能力 | 当前可复用基础 | 当前关键缺口 |
| --- | --- | --- |
| R1 异步执行 | 同步 RunEngine、Run/Result 持久化 | API 等待执行；无完整 CaseRun/Attempt、增量结果、可靠进度、并发/重试/取消/幂等 |
| R2 真实 Agent | `HttpTargetAdapter`、错误分类、Trace、规则评估和报告 | 对象注册偏硬编码；真实发现/版本/凭证/调用/Trace 仍有断点 |
| R3 真实 Skill | 领域已有 `TargetType.SKILL` 概念 | HTTP API 和测试仍以 Agent 为主，缺真实 Skill 端到端链路 |
| R4 LLM 评估器 | `LlmJudgeEvaluatorSpec`、`JudgeEvidence`、五态结果 | `resolve_judge` 尚未实现真实运行时，没有真实 Provider 闭环 |
| R5 用例生成 | Dataset/Case 校验、草稿和发布流程 | 缺 GenerationRequest、CandidateCase、生成、审核和草稿写入 |
| R6 结果对比 | 单 Case 重跑比较和报告 | 缺任意两个完整 Run 的可比性、汇总差异和逐 Case 下钻 |
| R7 根因分析 | Result、规则失败、输出和 Trace | 缺失败归组、证据选择、根因假设和反馈 |
| R8 A/B Test | 普通 Run、未来 R6 对比 | 缺实验配置、双 Run 编排、同 Case 配对和胜负约束 |

当前 Result 存储仍存在 `INSERT OR REPLACE` 覆盖风险。R1/R6/R8 前必须明确唯一性或 revision 语义，避免重试、比较和实验改变历史结果。

| 波次 | R | 用户获得的能力 | 主责 | 完成的核心证据 |
| --- | --- | --- | --- | --- |

| 第二波 | R7 | 理解 Badcase 的可能原因和下一步验证动作 | C | 失败归组、根因假设、证据、不确定性和反馈 |

### 2.4 依赖与并行关系

```text
R0 契约与真实条件
 ├─ A：R1 异步执行 ────────────────────────────────────┐
 ├─ B：R2 真实 Agent ──> R3 真实 Skill ────────────────┤
 └─ C：R4 LLM 评估器 ──────────────────────────────────┤
                                                         v
                                             G1 第一波联合验收
                                              ├─ E：R5 用例生成
                                              ├─ D：R6 完整 Run 对比 ──> R8 A/B
                                              └─ C：R7 Badcase 根因 ───> R8 结论约束
                                                                    |
                                                                    v
                                                        G2 Alpha 联合验收
```

R1、R2、R4 的开发不互相等待完整实现，但必须使用 R0 冻结的契约。R2 没有固定 Target/Connection 协议时，R3 只能准备测试，不能另建一套 Skill 流程。G1 未通过时，第二波不进入生产实现。

## 3. 第一波：每个 R 做什么、做到什么样

### 3.1 R0：契约与真实条件门禁

目标：让五个人使用同一套状态、外部协议、Judge 结构和验收数据，避免并行后返工。

| 责任人 | 在 R0 中负责什么 |
| --- | --- |
| A | Run/CaseRun/Attempt 状态、API 和迁移边界 |
| B | Connection、TargetRef、Agent/Skill 调用、版本、错误和 Trace 契约 |
| C | ModelProvider、Judge 输入输出、五态、证据和错误契约 |
| D | 进度、报告、Judge 和比较所需读取字段 |
| E | 真实脱敏数据、预期结果和验收脚本 |
| 项目负责人 | 冻结范围、批准契约、登记外部阻塞 |

真实外部条件必须明确：

- 可访问的 Sandbox/Base URL 和凭证引用。
- 至少一个真实 Agent、一个真实 Skill 及稳定 ID/版本。
- 实际调用模式、正常与异常响应、最终状态和取消能力。
- Trace 获取方式：`trace_id`、trace-sdk 事件流（新路径）或 OTLP（过渡保留）、查询接口。
- 本轮唯一 LLM Provider、模型、凭证、预算和结构化输出能力。

R0 完成标准：

- 四份最小契约均有唯一 Owner：Target、Run、EvaluationResult/Judge、ComparableRun/Experiment。
- 当前后端、前端、构建和关键 E2E 有通过/失败记录。
- 外部条件已验证；缺失项明确标为阻塞，不能用 Mock 标记真实完成。
- 第一波任务可直接引用契约和验收数据，不需各自重新解释语义。

### 3.2 R1：任务异步管理与可靠执行

用户能力：提交评测后立即获得 Run ID，可以离开页面；返回后看到真实进度、部分结果、错误、重试和取消结果。

| 责任人 | 在 R1 中负责的功能 |
| --- | --- |
| A（主责） | Run/CaseRun/Attempt；create/submit/dispatch/finalize；Dispatcher；增量持久化；数据库进度；错误隔离；并发、超时、重试、取消、幂等、中断识别和 Result 唯一性 |
| B | Agent/Skill 后台调用生命周期、超时/取消能力、Target 错误的可重试分类、Trace 关联 |
| C | 规则/Judge 的异步执行、Provider 超时/限流/预算、Evaluator ERROR 与质量 FAIL 区分 |
| D | 进度页、部分结果、刷新/离开返回、执行失败与质量失败的展示 |
| E | 快慢混合、部分失败、重复提交、重试、取消、中断等 E2E |

R1 完成标准：

- `submit_run` 在全部 Case 完成前返回 Run ID。
- 数据库是状态权威，页面不自行推测状态。
- 每个 Case 完成后立即写 Result/Trace，已完成结果可提前查看。
- 单个 Target、Trace 或 Evaluator 异常不抹掉其他结果。
- 有界并发；只重试明确可重试错误；每次重试有 Attempt 且不重复计分。
- 取消后不再派发新 Case，已完成结果保留；重复提交不产生重复 Run。
- 服务中断后的任务不会永久显示为 `running`；自动断点续跑暂缓，可明确中断并人工重跑。

### 3.3 R2：真实 HTTP Agent 评测与报告

用户能力：不修改 AgentGate 代码即可连接外部平台上的真实 Agent，固定版本、运行评测并查看真实报告。

| 责任人 | 在 R2 中负责的功能 |
| --- | --- |
| B（主责） | Connection/Secret 引用、连接检查、Agent 发现或手工引用、版本解析、真实 HTTP 调用、响应/错误归一化、Trace 关联和 TargetRef |
| A | TargetRef 进入 RunManifest，真实调用通过 Run 生命周期持久化 Result/Trace |
| C | 确定性 Evaluator 消费 TargetOutput/Trace，基础设施错误不误记为质量 FAIL |
| D | 连接和 Agent 选择；展示平台、ID、版本、输出、规则结果、错误和 Trace |
| E | 正常、错误凭证、对象/版本不存在、限流、超时和异常响应 E2E |

R2 完成标准：

- 实际访问真实外部服务，不是 Mock、录屏或手工插库。
- 报告固定平台、Agent ID/版本、Dataset 版本和 Run 配置。
- 至少一个 Case 能从结果下钻到真实输出、规则结果和真实 Trace。
- 认证、限流、超时、格式和对象不存在错误可理解且不泄露密钥。
- AgentGate 只读引用外部 Agent，不创建、修改或发布外部对象。

### 3.4 R3：真实 Skill 评测

用户能力：从与 Agent 相同的入口选择真实 Skill，执行相同评测并获得结构一致的报告。

| 责任人 | 在 R3 中负责的功能 |
| --- | --- |
| B（主责） | 去除固定 Agent 限制；支持 target_type；解析 Skill ID/版本/能力；调用真实 Skill；保存实际路由；复用 R2 错误和 Trace 协议 |
| A | Skill 复用 R1 Run/CaseRun/Attempt，不新增执行引擎；Skill 版本进入快照 |
| C | 路由/工具类规则和 Judge 对 Skill 输出的语义一致 |
| D | Agent/Skill 统一入口；展示 Skill ID/版本、实际路由和一致报告 |
| E | 正确路由、误路由、调用失败、版本缺失和 Trace 异常 E2E |

R3 完成标准：

- HTTP API 和 Run 配置不再强制 `TargetType.AGENT`。
- 真实 Skill 与 Agent 共用 Connection、TargetRef、Run、Result、Trace 和报告。
- 保存真实 Skill ID/版本及可获得的实际路由信息。
- 用户可以分别运行真实 Agent 和 Skill，结果字段和下钻能力一致。
- 本 R 是执行后评测，不包含静态 Skill 定义检查和完整路由混淆矩阵。

### 3.5 R4：真实 LLM 评估器

用户能力：为开放式输出启用 LLM 主观评价，看到分数、结论、理由和引用证据，并能区分模型错误与 Agent 质量问题。

| 责任人 | 在 R4 中负责的功能 |
| --- | --- |
| C（主责） | 唯一 ModelProvider、`resolve_judge`、Prompt 输入、结构化输出、五态、JudgeEvidence、模型/Prompt 快照、超时/限流/格式错误/预算和固定 Gate 策略 |
| A | Judge 配置进入 RunManifest；Judge 在 CaseRun 中执行和持久化，错误不阻断其他 Evaluator |
| B | 提供归一化 TargetOutput 和允许进入 Judge 的脱敏 Trace 摘要 |
| D | 最小 Judge 配置入口；展示分数、理由、证据、模型、REVIEW/ERROR 和成本信息 |
| E | 明显通过、明显失败、边界、缺密钥、超时、限流和格式错误 E2E |

R4 完成标准：

- 至少 5 个真实 Case 同时运行确定性规则和真实 LLM Judge。
- Provider、模型、Prompt、参数和目标版本进入快照。
- 输出经结构化校验，分数、理由和证据可追溯。
- Provider 错误形成 Evaluator `ERROR` 或 `REVIEW`，不算 Agent 质量 FAIL，也不抹掉规则结果。
- Fake Provider 只能证明契约测试，不能用于标记真实可用。
- 本 R 不建设多 Provider、模型市场、Hybrid 或完整 Gate 编辑器。

### 3.6 G1：第一波联合验收

联合旅程：

1. 配置一个真实外部平台连接。
2. 分别选择真实 Agent 和真实 Skill 的固定版本。
3. 选择已发布 Dataset、确定性规则和真实 LLM Judge。
4. 提交后台评测，离开并返回进度页。
5. 查看部分结果、完成结果、规则/Judge、错误和 Trace。
6. 取消一个运行，再运行一个包含可重试错误的评测。

G1 只有在 R1～R4 分别完成且联合旅程通过后才完成。任一能力只能在 Mock 下运行、组合后状态不一致、结果会被覆盖或密钥可能泄露时，第二波不启动。

## 4. 第二波：每个 R 做什么、做到什么样

### 4.1 R5：自动生成候选用例

用户能力：基于真实 Agent/Skill 信息生成候选 Case，人工编辑、接受或拒绝，接受项进入 Dataset 草稿。

| 责任人 | 在 R5 中负责的功能 |
| --- | --- |
| E（主责） | GenerationRequest、CandidateCase、批次状态；调用 C 的 Provider；结构校验/去重；候选页面；编辑/接受/拒绝；原子写入 Dataset 草稿；来源和审核记录 |
| C | 复用 R4 Provider、Secret、限流和结构化输出，不创建第二套模型调用层 |
| B | 提供 TargetDescriptor：对象类型、版本、描述、输入输出、工具和 Skill/意图 |
| A | 为生成批次复用提交、状态、错误、幂等和持久化能力 |
| D | 评审候选审核页面与现有 Dataset 体验的一致性 |

R5 完成标准：

- 使用真实对象元数据和真实 Provider 生成候选，不直接写已发布 Dataset。
- 无效结构和明显重复不会进入待接受列表。
- 用户能部分接受、部分编辑、部分拒绝；接受项原子写入草稿。
- 每个 CandidateCase 可追溯到 Target 版本、生成配置、模型/Prompt 和人工处理结果。
- 重复提交不产生重复批次；记录接受率和编辑率，不以生成数量代表价值。

### 4.2 R6：完整 Run 结果对比

用户能力：选择同一 Dataset 版本上的两个 Run，理解整体和逐 Case 的改善、退化、不变、缺失或不可比较。

| 责任人 | 在 R6 中负责的功能 |
| --- | --- |
| D（主责） | Run 选择、可比性、汇总差异、五态/指标/耗时、Case 配对分类、两侧输出/规则/Judge/Trace 下钻 |
| A | 提供不可变 RunManifest/Result 和稳定读取接口，修正 Result 覆盖风险 |
| C | 定义五态改善/退化、Judge 差异和 Gate/指标比较语义 |
| B | 提供两侧 TargetRef/版本差异和真实调用证据 |
| E | 改善、退化、不变、仅一侧存在、ERROR 和配置不一致夹具/E2E |

R6 完成标准：

- 第一版只比较同一 Dataset 版本和同一 Case 身份体系下的两个结束 Run。
- 明确展示 Target、Evaluator、Gate 和关键 RunConfig 差异。
- 显示总体通过率、五态、关键指标和耗时差异。
- 每个 Case 被分类，并能下钻两侧证据。
- 配置不同或样本缺失时明确“不完全可比”，不强行总结版本优劣。

### 4.3 R7：Badcase 根因辅助

用户能力：对 FAIL、REVIEW、ERROR 查看可能根因、证据、不确定性和下一步验证动作，并反馈结论是否有用。

| 责任人 | 在 R7 中负责的功能 |
| --- | --- |
| C（主责） | 确定性失败归组、代表 Case、脱敏证据、根因 Prompt、结构化假设、反证/不确定性、验证动作和反馈语义 |
| D | Badcase 分组、影响数量、根因假设、证据下钻、确认/驳回/证据不足页面 |
| B | 提供 Trace、路由、工具、对象版本和 TargetDescriptor 证据 |
| A | 为分析批次复用任务状态、错误、幂等和持久化 |
| E | 构造不同失败类别和证据不足样本，执行真实 Run 根因 E2E |

R7 完成标准：

- 先按规则、错误、路由/工具和输出特征确定性归组，再调用 LLM。
- 每个假设能跳回原 Case、Result 和 Trace 片段。
- 区分 Agent/Skill 行为、评测标准、测试数据和基础设施问题。
- 无证据时返回“证据不足”，不编造确定结论。
- 用户能确认、驳回或标记证据不足；系统不自动修改外部对象或 Dataset。

### 4.4 R8：受控 A/B Test

用户能力：在相同 Dataset、评估器和运行条件下比较两个对象版本，看到配对胜负、依据和结论限制。

| 责任人 | 在 R8 中负责的功能 |
| --- | --- |
| A（编排主责） | Experiment、共享配置校验、两侧普通 Run、状态、取消/重试/幂等和同 Case 结果聚合 |
| D（结果主责） | 两侧对象选择、双 Run 进度、总体差异、A 胜/B 胜/持平/失败/不可比和证据下钻 |
| B | 固定 A/B 两侧 TargetRef，校验对象类型/版本，处理单侧外部错误 |
| C | 定义五态/分数的胜负、样本量和不可下结论规则，防止 Judge ERROR 被当作胜负 |
| E | 准备胜负/持平/单侧失败/配置不一致夹具，执行真实对象版本 E2E |

R8 完成标准：

- 两侧使用相同 Dataset 版本、Case、Evaluator、Gate 和关键 RunConfig。
- 实验只编排两个普通 Run，不复制执行引擎或 Result。
- 结果按同一 Case 配对，展示胜负、持平、失败和不可比较。
- 页面可解释胜负来源、配置差异、样本量和限制。
- 样本不足时不宣称显著更优；不做在线分流、多臂实验、自动停止或自动发布胜者。

### 4.5 G2：内部 Alpha 联合验收

G2 验收八项完整用户旅程，并完成：

- 后端、前端、构建、类型检查和全旅程 Playwright。
- 数据迁移、重复提交、并发、取消、重试和故障注入。
- 密钥、日志、错误、Trace、Judge/根因输入输出的泄露检查。
- 较大 Dataset 的容量、SQLite 锁、外部限流和 Judge 成本验证。
- 演示数据、运行手册、已知限制和后续生产化触发条件。

## 6. 本轮明确暂缓

- 完整评估器资产管理和完整 Gate 管理。
- HTML/XLSX/CSV 报表导出。
- 多 Provider 路由、模型市场和 Hybrid。

## 7. 冲突控制和评审规则

### 7.1 同时工作的边界

- 同时最多三条关键实现主线。第一波默认 A/R1、B/R2-R3、C/R4；第二波默认 E/R5、D/R6、C/R7，R8 在 R6 契约稳定后启动。
- 每人同时只保留一个未进入评审的主任务。
- 每个任务必须能独立验收；过大的任务继续拆分。
- 每天至少合入或集成验证一次，不保留跨阶段大分支。
- 一个 R 进入验收后冻结范围，只修阻断问题。

## 10. 所有 R 的统一完成定义

一个 R 只有同时满足以下条件才能标记完成：

- 有一句普通用户能理解的能力承诺和一条完整演示脚本。
- 主路径无需修改代码、手工插库或替换持久化数据。
- 声称真实 Agent/Skill/LLM 时，实际访问对应外部服务；Mock 只算契约测试。
- 对象、Dataset、Evaluator/Prompt 和 RunConfig 版本可追溯。
- 正常、空、加载和关键异常状态完整。
- 数据库状态和实际执行一致；重试/重复提交不重复计分；历史结果不被静默覆盖。
- 明文密钥不进入数据库、API、日志、Trace、Judge 输入或报告。
- 领域规则有单元测试，API 有正常/异常测试，用户主旅程有 E2E。
- 后端、前端、类型检查/构建通过，已知限制有记录。

以下任一情况一票否决：

- 用户主旅程 E2E 未通过。
- 用 Mock、固定 JSON 或录屏冒充真实外部服务。
- Run 状态与实际执行不一致。
- 重试导致重复计分，或历史 Result 可被静默覆盖。
- 密钥可能进入日志、Trace、模型输入或报告。
- 根因和 A/B 在证据不足时给出确定性结论。
