# AgentGate 需求基线

> **文档状态**：草稿（review 中）
> **定位**：本文件是"评测系统要什么"的唯一权威，只陈述需求（做什么、为什么、做到什么程度），不陈述设计（怎么实现、如何组织）。本文件是 `product-requirements-zh.md`（简版需求）的详细展开：简版作为入口概览，本文件作为需求细目的权威陈述，两者不一致处以本文件为准。
> **与设计的关系**：需求不依赖任何既有的对象模型或模块划分，也不陈述实现与架构"如何承载这些需求"。
> **来源**：对旧需求文档与一份早期需求分析文档收敛，去除了其中的设计表述与内部过程内容。
> **配套**：待评审的设计假设、待澄清问题、关键裁定、需求补充项、开源卫生检查等评审信息，见 `requirements-review-agenda-zh.md`。

---

## 1. 背景与目标

企业做业务开发的工程人员，需要对 Agent 和 Skill 回答四个问题：

1. 它是否达到上线要求？
2. 失败发生在哪里？
3. 应该改 Agent、Skill、提示词，还是改评测用例？
4. 改完之后，是否比原版本更好？

围绕这四个问题，形成评测闭环：接入评测对象 → 准备评测集 → 配置评测标准 → 发起评测 → 查看结果与失败用例 → 定位原因并改进 → 更新对象或用例 → 回归评测。

---

## 2. 范围与边界

### 2.1 系统做什么

评测对象（Agent、Skill）的评价与质量保障：维护评测集、安排评测标准、执行评测、产出达标结论与失败分析。

### 2.2 系统不做什么

- 不创建、不修改、不管理被评测的 Agent 或 Skill，那些由外部的对象平台负责；本系统只读取并引用它们。
- 演示用的示例 Agent 和示例 Skill 只用于演示与端到端验证，不代表系统会接管对象资产。

### 2.3 交付与开源约束

- 不含任何特定企业的专有命名、业务逻辑、内部术语与技术栈。
- 不绑定单一厂商平台，同类对象平台均可接入。
- 不依赖商业云服务，可自建部署。
- 评测核心能力与外部平台解耦，经适配接入。

### 2.4 明确不做的事

| 不做 | 理由 |
| --- | --- |
| 安全合规类用例的生成 | 安全评测由专门的安全评测覆盖 |
| 词元消耗预估 | 现阶段无此需求 |
| 让用户手动填写"对象能力描述" | 系统直接从对象平台读取，不重复录入 |
| 完整版本血缘图 | 暂缓，待有明确需求再增补 |
| 文件与多模态产物评估 | 暂缓，待有明确需求再增补 |
| CI/CD 上线门禁集成 | 暂缓；门禁结论由单次评测提供（REQ-022），接入流水线待有明确需求再增补 |
| 调优建议采纳闭环 | 暂缓；改进建议默认人工确认（REQ-030），采纳状态跟踪待有明确需求再增补 |

## 3. 术语（领域语言）

> 括注内为概念的英文通用名，统一小写（common noun）；不表示类型名或模块名。代码中的类名、包名（如 `trace` 包）属实现层，另行约定，避免把概念固化成类型名。

| 术语 | 含义 |
| --- | --- |
| 评测对象 | 被评测的 Agent 或 Skill，由外部平台拥有 |
| 用例（case） | 一条评测输入及其期望，可含多轮 |
| 评测集（dataset） | 一组用例的集合，通过版本承载内容 |
| 评估器（evaluator） | 一条可复用、可固化的评测标准 |
| 评测运行（run） | 以某对象版本为对象、用某评测集输入，执行一轮判定并产出结果的活动 |
| 门禁（gate） | 对一次评测是否达标的判定 |
| 调用链（trace） | 一次评测执行的完整记录，含调用、耗时与层级 |
| 轨迹（trajectory） | Agent 一步步的动作与观察历史，区别于调用链（trace） |
| 达标线 / 阈值 | 门禁判定使用的分数线 |
| 权重 | 各指标在总分中的重要程度 |
| 阻断级 | 一票否决的失败级别 |
| 待复核（review） | 需人工复核的结果 |
| 不适用（N/A） | 用例没有可用的检查 |
| 评测出错（error） | 评测标准自身故障，区别于"对象失败" |
| 回归集 | 一种用于回归验证的评测集，名称由用户自定义，可复用并随评测执行 |
| 正向用例 / 负向用例 / 边界用例 | 用例分类：期望通过 / 期望被拒或纠正 / 临界情况 |

## 4. 需求与设计的边界判据

写需求和评审时，用两条自查，避免把设计写成需求：

- **领域语言**：这个词会不会出现在用户或评测专家描述"我如何做评测、我想要什么结果"的话里？会，是需求。
- **方案语言**：这个词只出现在代码、类图、架构文档里（对象类名、存储结构、校验机制、模块划分、传输格式）？是，是设计。

需求句只保留前者，删掉后者。例如"已发布评测集不可变"是需求，"用内容哈希校验"是设计。

## 5. 功能需求

本章是全文主体，按评测闭环的用户任务分组，而非按系统模块分组。每条需求带稳定编号、优先级与现状。

**优先级**：P0=评测闭环必需；P1=闭环可用后的关键增强；P2=后置，架构预留；P3=暂缓，仅记录需求方向，不作排期承诺。
**现状**：已可用 / 部分可用 / 未实现 / 待定。

**P0 闭环节点**：接入（REQ-002/003）→ 评测集（REQ-004/005/006/007/008）→ 评测标准（REQ-013/016）→ 执行（REQ-017/018/019）→ 结果（REQ-021/022/023/027），共 16 条，构成可跑通的最小评测闭环。
**P1**：REQ-001/011/012/014/024/025/026/033/034/037/039。
**P2**：REQ-010/015/020/028/029/030/031/032/035/036/038。
**P3**：REQ-009。

### 5.1 接入评测对象

#### REQ-001 接入评测对象

`P1 · 部分可用`

接入要评测的 Agent 或 Skill，评测时确定其具体版本。对象由外部平台管理和拥有，本系统只读取、不创建、不修改、不管理。

- 说明：P0 阶段用示例对象即可验证闭环，接入真实外部对象是增强，故列为 P1。
- 验收：可选择非示例的评测对象，并确定其版本用于评测；外部对象在本系统内只读。

#### REQ-002 评测对象版本固化

`P0 · 部分可用`

一次评测必须能明确"评的是哪个版本"，对象改版不影响已完成评测的可复现。无法从外部平台获得稳定版本标识时，记录其已发布部署身份，并显式声明可复现性受限。

- 验收：对象改版后，历史评测仍指向其评测时的版本。

#### REQ-003 统一评测方式

`P0 · 已可用`

Agent 与 Skill 共用同一套评测方式（提交、执行、采集结果），不为不同类型维护两套流程与报告。

- 验收：Agent 与 Skill 在同一入口评测，结果信息一致。

---

### 5.2 准备评测集

#### REQ-004 用例与评测集管理

`P0 · 部分可用`

支持用例与评测集的创建、编辑、复制、删除、归档。用例含分类（正向用例/负向用例/边界用例）、难度、备注与期望，并支持用户给用例自定义标签（一个用例可挂多个标签）。

- 规则：标签为完全自由输入，不预设标签库；预选标签/标签库等收敛能力按需后置，本期不做。
- 说明：标签作为用例的可复用元数据，后续供按标签采样（REQ-009）与失败聚类（REQ-028）使用，本期先落地"打标签"能力本身。
- 验收：能为用例新增、修改、删除自定义标签，且标签随用例保存；被删用例不误伤已发布版本的评测。

#### REQ-005 多轮对话用例

`P0 · 已可用`

用例可包含多轮对话，每一轮有独立输入与独立期望，评测时逐轮判定，而非只评最后一轮。

- 验收：多轮用例逐轮逐条判定。

#### REQ-006 用例期望

`P0 · 已可用`

每条期望说明"期待发生什么"与"期待不发生什么"，可分项指定：应调用的工具、禁止调用的工具、预期路由到的 Skill/意图、期望的业务状态、期望的输出内容、应遵循的规则。

- 规则：应调用与禁止调用的工具不能自相矛盾；预期路由目标在多 Skill/意图对象上声明，用于支撑路由准确性判定与路由混淆矩阵（REQ-039）。
- 验收：每类期望都能被对应评测标准消费，并给出明确判定。

#### REQ-007 版本与不可变

`P0 · 已可用`

评测集内容以版本承载：草稿可编辑、可丢弃；发布后内容不可变；改动通过新版本表达。

- 验收：修改草稿不影响已发布版本；基于某已发布版本的历史评测，不因后续改动而改变。

#### REQ-008 导入导出

`P0 · 部分可用`

评测集可导入导出，用于迁移与共享。支持结构化格式（JSON）与 Excel。

- 规则：导出仅限已发布版本，草稿不导出。
- 验收：导入导出保留多轮用例；导入出错时报告具体是哪些条目有问题，而非整体失败。

#### REQ-009 采样

`P3 · 待定`

评测集较大时，可按策略抽取一个可复现的子集做快速初筛（随机、按标签、风险优先、失败优先、冒烟、回归、全量）。结果中注明采样方式与比例。

- 验收：见评审议程。

#### REQ-010 自动生成用例

`P2 · 未实现`

基于评测对象的能力信息（提示词、技能描述、工具、输入输出定义）自动生成候选用例，供人工审核后收录。

- 规则：不生成安全合规类用例；生成结果默认待人工确认。
- 验收：生成的用例进入待审核状态，经确认后才进入正式评测集。

#### REQ-011 从结果页修正用例

`P1 · 未实现`

在查看结果时，若发现用例本身有误（难度、输入、期望不对），可直接修正并暂存，批量生成新版本，而非每次修改单独生成一个版本。

- 验收：修改可暂存、可批量应用、可追溯。

---

### 5.3 配置评测标准

#### REQ-012 评估器复用与固化

`P1 · 部分可用`

评估器独立于单次评测保存、复用；评测引用评估器的固化定义，同一评估器可在多次评测与对比实验中共享。

- 验收：同一评估器可在多次评测与 A/B 对比中复用；一次评测使用评估器的具体定义，不随其后续修改而变化。

#### REQ-013 确定性评测标准

`P0 · 已可用`

不依赖模型的、结果确定的评测：工具是否被调用、是否调用了被禁止的工具、路由到预期 Skill/意图是否正确、工具参数、最终业务状态、输出格式、预算、策略合规、执行轨迹是否确定。

- 规则：确定性标准不应产生歧义，命中即得结论。
- 验收：命中标准即给出明确的通过/失败与原因。

#### REQ-014 语义评测标准

`P1 · 未实现`

用大模型做开放式语义评测：正确性、完整性、业务语义合规、推理质量。

- 规则：记录评审准则与模型配置；评审提示与评分标准需固化，保证可复现。
- 验收：返回通过/失败、分数、原因；评审输出格式异常时按"评测出错"处理，不误判成"对象失败"。

#### REQ-015 组合评测标准

`P2 · 未实现`

把确定性标准与语义标准按权重组合成一个评测标准。

- 规则：权重为正；确定性（规则）评测在同一用例的评测链中优先执行；关键结构或字段校验失败时，可按运行配置终止后续评测并判失败。
- 验收：见评审议程（后置）。

#### REQ-016 结果五态

`P0 · 已可用`

每个评测标准输出分数与原因，结果用五种语义区分：通过 / 失败 / 待复核 / 不适用 / 评测出错。

- 规则：评测出错不等于对象失败；不适用不计入通过率。
- 说明：五态在 P0 即定义完整；P0 阶段仅确定性标准（REQ-013），暂不产生"待复核"，其来源为语义评测（REQ-014，P1）与人工标注（REQ-033）。
- 验收：评测出错不导致整次评测失败；五态在指标与门禁中正确分流。

### 5.4 发起并运行评测

#### REQ-017 评测运行配置

`P0 · 部分可用`

发起评测时可配置并发执行的用例数、单条超时、失败重试规则。并发数、超时时长、重试次数均可配置，具体量级不作限定。

- 规则：单条超时视为"评测出错"（对象未在时限内完成，区别于"对象失败"），可参与重试；重试仅针对基础设施故障与超时，不重试"答错或未通过"；重试次数设上限（可配置），覆盖原结果、不重复计分。
- 验收：配置生效；重试覆盖原结果、不重复计分。

#### REQ-018 评测执行状态

`P0 · 已可用`

一次评测有明确生命周期（排队中 → 运行中 → 完成 / 失败 / 取消），用户能看到进度。

- 验收：状态流转可观测、可解释。

#### REQ-019 异步并发执行

`P0 · 部分可用`

评测耗时且需要并发，支持提交后异步执行，不阻塞使用者。

- 规则：后台执行进度仅作展示，评测结果以平台记录为准；重复提交不重复执行。
- 验收：提交后可异步运行并回写结果。

#### REQ-020 排队与预约

`P2 · 未实现`

公共模型配额紧张时，支持排队、预约与资源状态可见。

- 验收：见评审议程（后置）。

#### REQ-038 对接外部任务调度系统

`P2 · 未实现`

支持对接外部已有的任务调度系统（客户/企业方现成的调度平台），将评测执行的调度与派发交由外部调度系统承担；评测核心逻辑不因调度实现不同而改变。

- 规则：内置调度实现为默认实现；对接外部调度时，评测执行的提交入口与结果回写保持不变，不为调度实现变更而改动评测核心。
- 验收：见评审议程（后置）。

#### REQ-036 断点恢复

`P2 · 未实现`

评测中途因基础设施故障中断后，可从断点恢复继续评测，不从头重跑；已完成的部分不重复执行。

- 验收：中断后恢复，已跑完的用例不重跑、不重复计分。

### 5.5 查看评测结果

#### REQ-021 指标结果

`P0 · 已可用`

一次评测运行结束后，展示该次运行的聚合指标——通过率（总通过率，及按评测标准、按用例类别（正向/负向/边界）、按难度的分类通过率）、得分（综合得分与分类得分）、分项准确率（Agent 路由、Skill 触发、工具调用）、失败分布（含 Badcase 分布）、耗时（总耗时与平均单用例耗时）、失败率、错误统计（不适用、评测出错）。

- 规则：不适用与评测出错不计入通过率，但须在结果中可见，不能静默抹掉。
- 验收：上述聚合指标与统计维度均可见；并给出总用例数、通过、失败、不适用、评测出错五类计数，供使用者复算通过率。

#### REQ-022 门禁判定

`P0 · 已可用`

一次评测必须给出明确的达标结论（通过 / 不通过）。

- 规则（判定顺序）：评测出错 → 不通过；有阻断级失败 → 不通过；有待复核项 → 不通过；没有可评分用例 → 不通过；否则按达标线判定。达标线、指标权重、阻断级别在发起评测前配置，三者互不绑定。
- 规则（门禁规格）：系统提供默认门禁；支持将达标线、指标权重、阻断级别保存为可复用、可命名的门禁规格，发起评测时选择其一绑定。
- 验收：每次评测产出明确的通过/不通过结论，且能解释"为什么不过"。

#### REQ-023 报告与下钻

`P0 · 部分可用`

能查看评测报告，从总览下钻到用例级，看到每个用例的输入、输出、评分、失败原因，以及期望与实际的对照、调用链。

- 验收：从总览到单用例可层层下钻，能看到判定依据。

#### REQ-024 对比两次评测

`P1 · 未实现`

对比任意两次评测（新旧版本、不同配置），看通过率变化、新增通过/失败、指标差异、门禁变化。

- 规则（可比性）：对比以两次评测使用同一评测集（版本）为前提；评测集不同时，先提示不可比，或仅对可对齐的用例子集进行对比。
- 验收：可对比任意两次评测，差异能定位到用例级（哪些用例通过↔失败），并给出通过率/指标变化与门禁结论变化。

#### REQ-025 结果导出

`P1 · 未实现`

结果与报告可导出。HTML、Excel(xlsx)/CSV 为本期必做格式；PDF、JUnit XML、JSON 等为后续可选扩展。

- 验收：HTML 与 Excel(xlsx)/CSV 均可完整导出，内容与页面结果一致。

#### REQ-026 回归评测

`P1 · 未实现`

支持把评测中发现的失败用例与核心通过用例加入一个用于回归验证的评测集（回归集）。回归集是精选高风险用例的快速回归子集，可自定义名称、创建后复用、随后续评测执行，用于低成本高频地验证修复与防止退化；它不是原评测集的复制。

- 验收：可把失败用例与核心通过用例加入回归集；回归集名称可自定义；回归集作为评测集被发起评测时可直接选用。

#### REQ-027 单用例重跑

`P0 · 已可用`

对单个用例单独重跑，验证修复或调整。

- 验收：单用例可独立重跑并查看结果。

### 5.10 安全

#### REQ-034 凭证与密钥

`P1 · 未实现`

AgentGate 保存的凭证与密钥（含接入外部对象平台的 API key/凭证、私有模型密钥等），由使用者提供并加密保存；页面、日志、结果、报告、导出与对外接口均不显示明文、不外泄。

- 验收：凭证与密钥不出现在任何结果、报告、导出、调用链、对外接口、日志中。

#### REQ-035 敏感信息脱敏

`P2 · 部分可用`

外部接入的调用链（trace）等数据不一定已脱敏：若采集侧已脱敏，则直接取用；若未脱敏，AgentGate 须在取用与展示前完成脱敏。脱敏机制予以保留，需要脱敏的字段范围与强度待确认外部数据是否已脱敏后再详细设计；当前阶段暂按「采集侧已脱敏」对待。

- 验收：当外部调用链未脱敏时，AgentGate 能在取用与展示前完成脱敏；具体脱敏的字段范围与强度待确认后按约定实现。

#### REQ-037 操作留痕与审计

`P1 · 未实现`

评测与结果的改动留痕、可追溯；结果写入后不可篡改；历史记录与报告可导出，用于审计。

- 验收：关键操作可追溯到人与时间；结果不因后续改动而变化；审计导出可用。

## 6. 非功能需求

本节只保留横切的质量属性；能被单条功能需求承接的要求不在此重复。

| 维度 | 要求 |
| --- | --- |
| 可复现 | 一次评测的对象版本（REQ-002）、评测集版本（REQ-007）、评测标准（REQ-012）、门禁配置（REQ-022）全部固化，可一键复跑，得到相同结果 |
| 可扩展 | 新增对象类型、评测标准类型、导入格式时，接入成本低 |
| 安全 | 数据按权限隔离（权限模型见下文「权限与隔离」） |
| 可开源性 | 核心评测能力与特定企业平台及其技术栈解耦；开源部分不含私有数据、客户信息与凭证，个人开发者与其他企业均可引用 |

密钥（REQ-034）、脱敏（REQ-035）、失败重试（REQ-017）、断点恢复（REQ-036）、操作留痕与审计（REQ-037）均已由功能需求承接。

性能指标（并发数、容量、延迟上限）的具体数值取决于实际部署规模，本期需求不预先给定固定值，待部署方案确定后再定义。

**权限与隔离**

AgentGate 支持两种权限来源：

- **独立使用**：AgentGate 自行维护团队与角色权限，支持单人（使用者即管理员）与多人协作（团队隔离 + 角色）。
- **对接外部平台**：以外部对象平台的权限为权威源，做权限对等。

权限对等（对接模式）：
- 使用者在 AgentGate 内，对某评测对象及围绕它产生的全部数据（评测集、评测任务/运行、结果与报告、调用链、日志、操作记录、接入配置）的可见与操作权限，不超出该使用者在外部平台对相应评测对象的权限；外部平台未授权的，AgentGate 内同样不可见、不可操作。
- 各外部平台的权限模型可能存在差异，AgentGate 不绑定任一模型；「对等」是结果要求，具体映射属于实现适配。无法从外部平台取得权限信息的，按无权限处理（fail-closed）。

角色（独立协作模式）：管理员（管理成员与全部资源）／成员（创建/编辑评测集与评估器、发起评测）／只读（查看结果与报告）。

系统管理员例外：AgentGate 系统管理员可跨团队、跨对象查看全部上述数据（含日志与操作记录），不受对等限制。

## 7. 关键决策

需求层面的取舍，作为设计与开发的约束：

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 达标线、指标权重、阻断级别三者分离，均在使用者发起评测前配置 | 三者是不同的语义，不应绑定 |
| D2 | 静态检查后置（P2），不作为本期闭环必需能力 | 非评测闭环的必经环节 |
| D3 | 异步并发执行属闭环必需（P0），排队/预约后置（P2） | 前者是"评测能跑起来"的前提，后者是资源体验增强 |
| D4 | 多轮对话逐轮判定，而非只评最后一轮 | 路由类多轮场景需要逐轮判定 |
| D5 | 评测对象由外部拥有，本系统只读并引用 | 评测系统不接管对象资产 |
| D6 | 判定只给结论与可解释理由，不做自动修复 | 改进建议须人工确认后方可执行 |
